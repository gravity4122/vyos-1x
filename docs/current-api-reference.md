# Current VyOS HTTP API Reference

## Purpose

This document describes the API functionality currently present in this
codebase. It is intended as the working reference before adding the GUI API
modules.

Project-specific UI rule:

- Do not use the term "VyOS" anywhere in user-facing GUI text, page titles,
  navigation, labels, notifications, dialogs, bundled frontend metadata, or
  visible assets.
- Use wording such as "DevGate", "router", "system", or "device" in the UI.
- This API reference may still mention existing VyOS backend package names,
  code paths, modules, and APIs because those are the current implementation
  details the GUI must integrate with.
- For any GUI, frontend, visual design, interaction design, layout, or
  user-experience development, use the project-specific `ui-ux-pro-max`
  standard. GUI work must be treated as a high-quality product design task, not
  only a functional form wrapper: clear workflows, polished controls,
  responsive layouts, accessible states, consistent terminology, careful error
  handling, and production-grade usability are required.

The current API is implemented by:

- `src/services/vyos-http-api-server`
- `src/services/api/rest/routers.py`
- `src/services/api/rest/models.py`
- `src/services/api/graphql/`
- `python/vyos/configsession.py`
- `src/conf_mode/service_https.py`
- `data/templates/https/nginx.default.j2`

## Runtime Architecture

```text
Client
  -> HTTPS nginx listener from service https
  -> nginx proxy for API paths
  -> unix socket /run/api.sock
  -> vyos-http-api-server
  -> FastAPI app
  -> shared ConfigSession
  -> VyOS CLI/config backend
```

The API server is started by `vyos-http-api.service`, generated from
`data/templates/https/vyos-http-api.service.j2`.

The API server listens on:

```text
/run/api.sock
```

Nginx proxies selected HTTP paths to that socket.

## Enabling The API

The API is configured under:

```text
service https api
```

Important CLI nodes:

```text
service https api keys id <id> key <key>
service https api rest
service https api rest strict
service https api graphql
service https api graphql introspection
service https api graphql authentication type key
service https api graphql authentication type token
service https api graphql authentication expiration <seconds>
service https api graphql authentication secret-length <bytes>
service https api graphql cors allow-origin <origin>
```

Commit validation requires at least one valid API key unless GraphQL token
authentication is enabled.

## Response Envelope

REST endpoints use this response shape:

```json
{
  "success": true,
  "data": {},
  "error": null
}
```

Error shape:

```json
{
  "success": false,
  "data": null,
  "error": "message"
}
```

## Authentication

### REST Authentication

REST endpoints require an API key in the JSON body:

```json
{
  "key": "id_key"
}
```

The key is checked against keys loaded from `/run/http-api-state`, generated by
`service_https.py`.

REST authentication is implemented in `src/services/api/rest/routers.py`:

- `check_auth()`
- `auth_required()`

### GraphQL Authentication

GraphQL supports two authentication modes:

```text
key
token
```

With `type key`, each GraphQL operation includes:

```graphql
data: { key: "id_key" }
```

With `type token`, a JWT is generated with the `AuthToken` mutation and sent as:

```text
Authorization: Bearer <token>
```

Token authentication uses PAM for username/password validation and an in-memory
secret generated at API initialization time.

Query parameters:

### `POST /configure`

Feature:

- Apply simple config-mode operations.
- Supports single command or command list.
- Commits automatically after staging changes.
- Supports commit-confirm.
- Supports background execution with `?in_background=true`.

Operations:

```text
set
delete
comment
confirm
```

Single command body:

```json
{
  "key": "id_key",
  "op": "set",
  "path": ["system", "host-name"],
  "value": "vyos-router",
  "confirm_time": 0
}
```

Command list body:

```json
{
  "key": "id_key",
  "commands": [
    {
      "op": "set",
      "path": ["system", "host-name"],
      "value": "vyos-router"
    },
    {
      "op": "set",
      "path": ["system", "name-server"],
      "value": "1.1.1.1"
    }
  ],
  "confirm_time": 0
}
```

Confirm body:

```json
{
  "key": "id_key",
  "op": "confirm"
}
```

Backed by:

- `ConfigSession.set()`
- `ConfigSession.delete()`
- `ConfigSession.comment()`
- `ConfigSession.commit()`
- `ConfigSession.commit_confirm()`
- `ConfigSession.confirm()`
- `ConfigSession.discard()`

Important behavior:

- A global lock serializes config changes.
- If commit fails, the session is discarded.
- If `service https` changes, commit may be scheduled in the background so the
  API can return before reloading itself.
- With `rest strict`, delete checks that the path/value exists before deleting.

Feature:

Operations:

```text

```

Set section body:

```json
{
  "key": "id_key",
  "op": "set",
  "path": ["interfaces", "ethernet", "eth0"],

    "address": ["dhcp"]
  }

```

Load section body:

```json
{
  "key": "id_key",
  "op": "load",
  "path": ["interfaces", "ethernet", "eth0"],
  "section": {

    "address": ["dhcp"]
  }
```

Tree body:

```json
{
  "key": "id_key",
  "op": "load",
  "mask": {
    "inclusive": "<serialized inclusive mask>",
    "exclusive": "<json list of excluded paths>"
  },
  "config": {
```

Backed by:

Important behavior:

- `load` deletes the existing section before setting the submitted section.
- Tree load requires mask data to avoid damaging unrelated config.
- Uses the same commit, lock, discard, and self-reload behavior as
  `/configure`.

Feature:

- Read status of background operations created by `/configure` or
  `/configure-section` with `?in_background=true`.

Query parameters:

```text

```

Body:

No model body is required by the route, despite using `POST`.

Returns:

```json
{
  "operations": [
    {
      "op_id": "...",
      "created_at": 0,
      "started_at": 0,
      "finished_at": 0,
      "status": "queued|running|succeeded|failed",
      "result": "...",
      "error": "..."
    }
  ]
}
```

Backed by:

- `BackgroundOpManager`

Important behavior:

- Queue is in-memory.
- Default max queue size is 128.
- Operation history is bounded and not persistent across API restarts.

```json
  "op": "load",

}
```

```json

  "op": "merge",
  "string": "system { host-name vyos-router }",
  "destructive": false,
  "confirm_time": 0
}
```

Backed by:

- `ConfigSession.save_config()`
- `ConfigSession.migrate_and_load_config()`
- `ConfigSession.merge_config()`
- `ConfigSession.commit()`
- `ConfigSession.commit_confirm()`
- `ConfigSession.confirm()`

Important behavior:

- If `file` is omitted for `save`, defaults to `/config/config.boot`.
- If `string` is used, the API writes it to `/tmp/config.file`.
- `load` migrates config before loading.
- `merge` supports destructive merge.
- `service https` self-reload behavior is handled like `/configure`.

## Multipart/Form Compatibility

REST routes use a custom `MultipartRequest` and `MultipartRoute`.

Supported form behavior:

- Converts `multipart/form-data` or `application/x-www-form-urlencoded` into
  JSON-like request bodies.
- Expects a `data` form field containing JSON.
- Can merge `key` from a form field into the parsed body.

This exists for compatibility with older HTTP API clients.

## Background Commit Behavior

The REST config path detects changes under:

```text
service https
```

If the change affects `service https`, the API schedules commit work after the
HTTP response where needed. This avoids killing/reloading the API server before
the response is sent.

Implication for GUI:

- GUI must poll `/retrieve/background-operations` when using background mode.
- GUI must handle API reload/disconnect after modifying HTTPS/API settings.

## Current API Gaps For GUI Work

The current API can already configure and operate the router, but a GUI needs
additional API affordances:

1. Dangerous operations rely on clients to add confirmation.
2. Most broad op-mode REST endpoints accept arbitrary paths and should be
   constrained by GUI metadata.
3. Background operation state is in-memory only.

## Recommendations For GUI Development

1. Build the GUI API as a new `/gui/*` namespace.
2. Reuse `ConfigSession` for all writes.
3. Reuse `/configure-section` semantics for structured module forms.
4. Use `data/reftree.cache` as the config schema source.
5. Use `data/op_cache.json` and `data/op-mode-standardized.json` as op-mode
   metadata sources.
6. Keep commit-confirm support visible in the GUI.
7. Add confirmation wrappers around reboot, poweroff, reset, image delete, and
   config load/merge.
8. Keep existing REST and GraphQL APIs stable for backward compatibility.
